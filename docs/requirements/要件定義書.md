# 要件定義書 — Daily Diary

> 本書は「何を作るか」を定義する。設計の詳細は [基本設計書](../basic-design/基本設計書.md) / [詳細設計書](../detail-design/詳細設計書.md) を参照。

## 1. プロジェクト概要

### 1.1 背景
個人の振り返り・気分記録・思考整理の習慣化を支援するツールへのニーズが高い。既存サービスは多機能化により学習コストが高いか、もしくはプライバシー面の不安があるかのいずれか。**SSO による手軽な開始** と **シンプルな1日1ページ** に絞った Web アプリで、書く習慣の入口を提供する。

### 1.2 目的・ゴール
- 利用者が毎日1分以内に日記を書き始められること
- 過去の振り返りを容易にし、書く習慣を継続させること
- 認証・データ保護で利用者の心理的負担をゼロにすること

### 1.3 解決したい課題
| 課題 | 影響 | 本サービスの対応 |
|---|---|---|
| 既存サービスのアカウント作成が面倒 | 着手障壁 | Google SSO だけでサインアップ |
| 入力項目が多くて続かない | 離脱 | 1日1エントリ、タイトル＋本文のみ |
| 過去日記の発見性が低い | 振り返り不能 | 日付ベースのカレンダー / 一覧導線 |
| プライバシー懸念 | 利用控え | プライベート専用、SSO以外の認証は持たない |

### 1.4 KPI / 成功指標
| 指標 | 定義 | MVP 目標 |
|---|---|---|
| DAU | アクティブ利用者数 | — (β計測のみ) |
| 7日継続率 | 登録から7日以内に3日以上投稿 | 30% |
| 平均投稿日数 / 月 | 1利用者あたりの月間投稿日数 | 10日 |
| ログイン成功率 | SSO ログイン試行のうち完了した割合 | 99% |

## 2. スコープ

### 2.1 対象範囲（MVP）
- Google SSO によるサインアップ・ログイン・ログアウト
- 当日の日記投稿（タイトル＋本文）
- 過去日記の閲覧・編集・削除
- 日記一覧（直近・カレンダー）
- アカウント情報の確認・退会

### 2.2 対象外（MVP ではやらない）
- メール+パスワード認証
- Google 以外の IdP（GitHub / Apple 等）
- 公開・共有・SNS連携
- 画像 / 音声 / 動画の添付
- 全文検索・タグ・カテゴリ
- 編集履歴 / バージョン管理
- モバイルネイティブアプリ
- 多言語化（初版は日本語のみ）

### 2.3 前提・制約条件
- 利用者は Google アカウントを保有
- 対応ブラウザ: モダンブラウザ最新2世代（Chrome / Edge / Safari / Firefox）
- 個人情報保護法（日本）に準拠
- データ保管リージョン: 日本国内

### 3.2 利用者の役割
| 役割 | 説明 | MVP スコープ |
|---|---|---|
| 一般利用者 (User) | 日記を書く・読む人 | ◯ |
| 運用管理者 (Admin) | 障害対応・通報対応 | △（運用手順のみ、画面なし） |

### 3.3 ペルソナ
**「平岡 はるか」 28歳・会社員 / 一人暮らし**
- 朝の通勤中（10分）・寝る前（10分）にスマホでログを残したい
- 既存の日記アプリで挫折した経験あり。理由は「広告」「操作の複雑さ」「強制的なSNS要素」
- Google アカウントは普段使い。新規パスワードを覚えるのは面倒

### 3.4 カスタマージャーニー（概要）
1. ランディング → 「Google でログイン」をタップ
2. SSO 承認 → 初回ログインで自動的にアカウント作成
3. 今日の日付の入力欄が中央に表示される
4. タイトルと本文を書いて保存 → 「保存しました」のフィードバック
5. 翌日以降、カレンダーから振り返り、必要なら過去日記を編集

### 5.3 ユースケース記述（抜粋）

#### FN-AUTH-01: SSO ログイン
- **事前条件**: 利用者が有効な Google アカウントを持っている
- **主シナリオ**:
  1. 利用者がランディング画面 (SC-01) で「Google でログイン」を押す
  2. システムが Google IdP に Authorization Request を送る（PKCE 付き）
  3. 利用者が Google で認証・同意
  4. システムがコールバックで認可コードを受け取り、ID Token を取得・検証
  5. システムが対応する User を特定（無ければ自動作成）し、セッションを発行
  6. システムがダッシュボード (SC-02) にリダイレクト
- **代替シナリオ**: 利用者が同意を拒否した場合、SC-01 に戻りエラーメッセージを表示
- **例外**: ID Token 検証失敗 → 認証エラー画面、5分後に再試行可

#### FN-DIARY-01: 当日の日記投稿
- **事前条件**: ログイン済み、当日分のエントリがまだ存在しない
- **主シナリオ**:
  1. 利用者が SC-02 で「今日の日記を書く」を押す → SC-03 へ
  2. 利用者がタイトル・本文を入力して「保存」を押す
  3. システムが `(user_id, today)` でエントリを作成
  4. システムが保存成功を表示し、SC-02 に戻る
- **例外**: 既に当日分が存在する → 編集画面 (SC-05) にリダイレクト

#### FN-DIARY-03: 過去日記編集
- **事前条件**: ログイン済み、対象エントリの所有者である
- **主シナリオ**:
  1. 利用者が SC-04 から対象日のエントリを開く → SC-05
  2. 利用者がタイトル・本文を編集して「更新」を押す
  3. システムが `updated_at` を更新して保存
  4. システムが SC-05 に「更新しました」を表示
- **例外**: 他人のエントリへの不正アクセス → 403 Forbidden

## 6. 非機能要件

### 6.1 性能・スケーラビリティ
| 項目 | 要件 |
|---|---|
| 画面表示応答 | 95%tile 1.0秒以内 |
| API 応答 | 95%tile 300ms 以内 |
| 同時接続 | MVP: 1,000 同時利用 |
| データ規模 | 利用者 10万人 × 1人あたり最大 365日 × 3年 = 約 1億行 を見据えた DB 設計 |

### 6.2 可用性
| 項目 | 要件 |
|---|---|
| SLO | 月間 99.5% |
| メンテナンス窓 | 月1回・深夜帯・30分以内 |
| RTO | 4時間 |
| RPO | 1時間 |

### 6.3 セキュリティ
- 認証は **SSO のみ**、パスワード保管は持たない
- セッションは httpOnly / Secure / SameSite=Lax Cookie で管理
- 通信は全て HTTPS (TLS 1.2 以上)
- 個人情報（メールアドレス・表示名・日記本文）は **保管時暗号化** (AES-256)
- OWASP Top 10 対策（CSRF / XSS / SQLi / SSRF など）を全 API に適用
- ID Token 検証は `iss`, `aud`, `exp`, `nonce`, 署名すべて検証

### 6.4 運用・保守性
- ログ: アプリケーション / アクセス / 監査の3系統、保管 90日
- 監視: 主要 API のエラー率・応答時間・SLO バーンレート
- バックアップ: DB を1時間毎にスナップショット、世代は7日

### 6.5 ユーザビリティ・アクセシビリティ
- WCAG 2.1 AA 相当に準拠
- キーボード操作で全主要機能を完結可能
- モバイル / デスクトップ両対応のレスポンシブ

### 6.6 法令・コンプライアンス
- 個人情報保護法（日本）
- プライバシーポリシー / 利用規約の同意（初回ログイン時）
- データポータビリティ: 退会時に利用者へエクスポート提供（将来検討）

## 7. 用語集

| 用語 | 説明 |
|---|---|
| SSO | Single Sign-On。本プロジェクトでは OIDC を用いた Google 連携を指す |
| IdP | Identity Provider。本プロジェクトでは Google |
| OIDC | OpenID Connect。OAuth 2.0 上の認証プロトコル |
| PKCE | Proof Key for Code Exchange。認可コード横取り防止 |
| エントリ (Entry) | 1件の日記。`(user_id, entry_date)` で一意 |
| セッション (Session) | ログイン状態を表すサーバ側レコード |
