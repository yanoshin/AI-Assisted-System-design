# インフラ設計インタビュー

質問に答えていくとインフラ構成の主要決定が固まります。回答は [`design.md`](design.md) に記入。Claude に進めてもらう場合は「infrastructure のインタビューを進めて」と依頼。

質問の体裁は **目的 / 選択肢 / 推奨デフォルト / 参考** の4要素。

---

## H. ホスティング前提

### Q-HOST-01: ホスティング種別は？
**目的**: 全体方針の起点。
**選択肢**:
- A. **パブリッククラウド単独** — AWS / GCP / Azure 等のいずれか1社
- B. **マルチクラウド** — 複数クラウドにまたがる
- C. **オンプレ単独** — 自社データセンター
- D. **ハイブリッド** — クラウド + オンプレ

**推奨デフォルト**: A
**参考**: [service-mapping.md](service-mapping.md)

### Q-HOST-02: クラウド選定は？（A / B / D の場合）
**選択肢**:
- A. **AWS** — シェア最大、サービス最多
- B. **GCP** — Kubernetes / データ系 / Google エコシステム
- C. **Azure** — Microsoft 製品との親和性、エンタープライズ
- D. **その他** — Cloudflare / Vercel / Fly.io / Render など PaaS

**推奨デフォルト**: A
**参考**: 採用後は [service-mapping.md](service-mapping.md) の該当列を参照

### Q-HOST-03: リージョン / マルチリージョン要否は？
**選択肢**:
- A. **単一リージョン** — シンプル・低コスト
- B. **アクティブ-スタンバイ** — DR 用にスタンバイを別リージョン
- C. **アクティブ-アクティブ** — 複数リージョンで同時稼働
- D. **エッジ配信のみ** — CDN/Edge で配信、バックエンドは単一

**推奨デフォルト**: A
**参考**: RTO / RPO は Q-DR-01

## I. コンピュート

### Q-COMP-01: コンピュート種別は？
**選択肢**:
- A. **VM** — 制御度高い、レガシー互換
- B. **コンテナ (マネージド)** — ECS / Cloud Run / AKS
- C. **コンテナ (Kubernetes)** — 大規模・複雑系
- D. **サーバレス関数** — Lambda / Functions

**推奨デフォルト**: B
**参考**: [service-mapping.md §コンピュート](service-mapping.md)

### Q-COMP-02: 配信は？
**選択肢**:
- A. **同一サーバ** — Web/API を1プロセスで
- B. **Web/API 分離** — フロント配信と API を別レイヤに
- C. **CDN + Edge SSR** — エッジで SSR
- D. **完全静的 + API** — フロント静的 + API バックエンド

**推奨デフォルト**: B

## J. ネットワーク

### Q-NET-01: ネットワーク分離は？
**選択肢**:
- A. **VPC + パブリック/プライベートサブネット** — 標準的
- B. **VPC + プライベートのみ + Bastion** — DB のみ厳格
- C. **シンプル単一サブネット** — 小規模・検証用
- D. **オンプレ既存ネットワーク** — VPN / 専用線

**推奨デフォルト**: A

### Q-NET-02: パブリック公開範囲は？
**選択肢**:
- A. **CDN + LB を公開、それ以降はプライベート**
- B. **API も直接公開（CDN なし）**
- C. **VPN 経由のみ（社内ツール想定）**

**推奨デフォルト**: A

### Q-NET-03: WAF / DDoS 対策は？
**選択肢**:
- A. **クラウドマネージド WAF** — AWS WAF / Cloud Armor / Front Door
- B. **CDN 付属の防御** — Cloudflare / Fastly
- C. **不要 / 最小限** — 内部ツール

**推奨デフォルト**: A

## Q. 環境戦略

### Q-ENV-01: 用意する環境は？
**目的**: 開発・検証・本番のライフサイクルを分離する単位を決める。
**選択肢**:
- A. **dev + prd** — 2環境最小構成
- B. **dev + stg + prd** — 一般的な3環境（検証を本番前に挟む）
- C. **個別開発者環境 + dev + stg + prd** — 開発者ごとに独立環境
- D. **PR ごとのプレビュー環境を追加** — B または C に加え、PR ごとに使い捨て環境

**推奨デフォルト**: B
**参考**: [`design.md` §11 環境構成](design.md)

### Q-ENV-02: 環境間の分離レベルは？
**目的**: 障害・課金・権限の漏れ範囲を決める。
**選択肢**:
- A. **同一プロジェクト内で名前空間 / タグで分離** — 簡素、安価
- B. **プロジェクト分離（GCP プロジェクト / AWS アカウント別）** — 強い分離、推奨
- C. **リージョン分離** — 同一プロジェクトで別リージョン
- D. **完全別組織（別請求アカウント）** — 大企業 / 厳しい監査要件

**推奨デフォルト**: B

### Q-ENV-03: ステージング環境のデータは？
**目的**: 検証の精度とプライバシーリスクのバランス。
**選択肢**:
- A. **空 / 開発時に投入** — 法務リスクなし、検証は限定的
- B. **合成データ（シード）** — 安全、量も調整可
- C. **本番のサニタイズコピー** — 個人情報を除去 / 仮名化したクローン
- D. **本番のフルコピー** — 法務・規約要確認、検証精度最高

**推奨デフォルト**: B
**参考**: 個人情報保護法、利用規約での扱い

### Q-ENV-04: フィーチャーフラグは？
**目的**: リリースとデプロイの分離、段階的ロールアウト。
**選択肢**:
- A. **不要** — デプロイ = 公開でよい
- B. **環境変数で対応** — 軽量、コード分岐
- C. **専用 SaaS (LaunchDarkly / Split.io / ConfigCat)** — 動的切替、UI 管理
- D. **OSS (Flagsmith / Unleash)** — セルフホスト

**推奨デフォルト**: A（MVP）→ 段階的に B / C

## R. ローカル開発環境

### Q-LOCAL-01: ローカルで動かす範囲は？
**目的**: 開発者の手元で完結する範囲を決める。
**選択肢**:
- A. **すべてローカル** — Docker Compose 等で DB も含めて手元完結
- B. **DB だけクラウド** — アプリはローカル、DB は Cloud SQL Proxy 等で接続
- C. **すべてリモート** — Codespaces / GitPod / Devbox で全部クラウド
- D. **ハイブリッド** — 一部のみクラウド依存（IdP やストレージ）

**推奨デフォルト**: A
**参考**: [`design.md` §12 ローカル開発環境](design.md)

### Q-LOCAL-02: ローカル DB は？
**目的**: ローカル開発で使う DB の調達方法。
**選択肢**:
- A. **Docker Compose（PostgreSQL / MySQL 公式イメージ）** — 環境差なし
- B. **ローカルインストール（Homebrew / apt 等）** — 軽量、習熟者向け
- C. **クラウド DB に Auth Proxy で接続** — 本番に近い、コストかかる
- D. **代替 DB（SQLite 等）** — 開発時のみ別 DB、要互換性検証

**推奨デフォルト**: A

### Q-LOCAL-03: ローカルでの認証（SSO 採用時）は？
**目的**: 開発時に OIDC をどう扱うか。
**選択肢**:
- A. **本物の IdP（開発用クライアント）** — Google 等に dev 用 OAuth クライアントを発行
- B. **モック IdP（mock-oauth2-server 等）** — オフラインでも動く、IdP 不要
- C. **認証バイパス（開発時のみ固定ユーザー）** — 最速だがコードに `if (dev)` が混じる
- D. **テストユーザーをシード** — DB に固定ユーザーを置き、OIDC は通常通り

**推奨デフォルト**: A（dev OIDC クライアント） + D（テストユーザー）

### Q-LOCAL-04: ローカルのシークレット管理は？
**目的**: 開発者の手元で機密値をどう保管・配布するか。
**選択肢**:
- A. **`.env.local`（gitignore）+ `.env.example`** — シンプル、共有は別経路
- B. **SOPS / git-crypt** — 暗号化してコミット
- C. **direnv + クラウド Secret Manager** — クラウド連携、設定がやや手間
- D. **1Password / Doppler 等の SaaS** — UI管理、チーム共有が楽

**推奨デフォルト**: A

### Q-LOCAL-05: 開発環境セットアップ自動化は？
**目的**: 新規参加者の立ち上げ時間を最小化する。
**選択肢**:
- A. **README + Makefile / シェルスクリプト** — 標準的
- B. **Devcontainer（VS Code / GitHub Codespaces）** — エディタ込みで完全再現
- C. **Nix / mise / asdf** — 言語ランタイム含めて宣言的管理
- D. **なし（手動）** — ドキュメントのみ

**推奨デフォルト**: A
