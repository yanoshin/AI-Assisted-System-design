# ADR 0003: 1日1エントリ制約の採用

- **Status**: Accepted
- **Date**: 2026-05-25

## Context

「毎日の日記を投稿」できる Web アプリ。1日に複数のエントリを許すかどうかは UX とデータモデルに大きく影響する。

選択肢:
- **A: 1日1エントリのみ**（同じ日付には1件しか作れない）
- **B: 1日複数エントリ可**（タイムライン的な体験）

## Decision

**A: 1日1エントリ制約を採用** する。

- DB レベル: `diary_entries (user_id, entry_date) UNIQUE`
- API レベル: `POST /api/diary-entries` は当日固定。重複時は `409 E_DIARY_DUPLICATE` を返し、クライアントは編集画面 (SC-05) へ誘導
- ビジネスルール: [詳細設計書 §1.3 BR-01](../detail-design/詳細設計書.md#13-ビジネスルール)

## Consequences

### Good
- 「今日のページ」が1つに定まるため UX が単純で、書く障壁が下がる
- データモデルがシンプルで、一覧・カレンダー表示の実装が容易
- 「過去日記の編集」が `日付` で一意に識別可能（パスにそのまま使える）

### Bad / Trade-offs
- 1日に何度も投稿したい利用者の体験を制限する
- 「複数エントリ可」に後で変更する場合、UNIQUE 制約と API パス (`/{date}`) の見直しが必要

## Alternatives

### B: 1日複数エントリ可
- API: `POST /api/diary-entries` で都度作成、リソース ID は `entry_id`
- UNIQUE 制約なし、`(user_id, entry_date)` は INDEX のみ
- UX: タイムライン or 「追記」スタイル

採用しなかった理由: ペルソナ（[要件定義書 §3.3](../requirements/要件定義書.md#33-ペルソナ)）は「毎日1ページに振り返りを残す」ニーズが中心で、複数エントリは過剰機能。MVP では複雑さを避ける。

## 将来の見直しトリガー

- ベータ利用者から「1日に複数書きたい」要望が一定数（10%超）寄せられた場合
- 競合サービスの調査でタイムライン型の優位性が明確になった場合
