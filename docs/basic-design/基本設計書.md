## 1. システム方式設計（アーキテクチャ）

### 1.1 全体構成
3層 + 外部 IdP のシンプルな Web アーキテクチャ。クライアントは SSR + クライアントサイドハイドレーション。

- 構成図: [architecture/component.mmd](architecture/component.mmd) — [README](architecture/README.md)

### 1.2 技術スタック（推奨）
> 実装は本リポジトリのスコープ外だが、整合性確認のため代表的な選定例を示す。
> 決定プロセス（インタビュー形式の雛形）と候補カタログは [`docs/tech-stack/`](../tech-stack/) を参照。

| レイヤ | 技術候補 | 備考 |

| フロントエンド | Next.js (React) | SSR + Edge 配信 |
| バックエンド | Node.js + Fastify / Hono | TypeScript |


## 4. 機能設計

### 4.1 機能 × 画面 × API マトリクス
| 機能ID | 画面 | 主要 API |
|---|---|---|
| FN-AUTH-01 | SC-01 | `POST /api/auth/login`, `GET /api/auth/callback` |
| FN-AUTH-02 | SC-02, SC-06 | `POST /api/auth/logout` |
| FN-AUTH-03 | (SC-01 連動) | `GET /api/auth/callback`（自動作成） |
| FN-AUTH-04 | SC-06 | `DELETE /api/me` |
| FN-DIARY-01 | SC-03 | `POST /api/diary-entries` |
| FN-DIARY-02 | SC-04, SC-05 | `GET /api/diary-entries`, `GET /api/diary-entries/{date}` |
| FN-DIARY-03 | SC-05 | `PUT /api/diary-entries/{date}` |
| FN-DIARY-04 | SC-05 | `DELETE /api/diary-entries/{date}` |

### 4.2 主要機能の処理方針
- **SSO 初回ログイン時のアカウント紐付け**: `(provider, providerSubject)` で既存 `SsoIdentity` を検索 → なければ User を新規作成し SsoIdentity を発行
- **1日1エントリ制約**: API 層と DB 層の二重保証（DB は UNIQUE 制約、API は事前 SELECT で409返却）
- **編集ロック**: MVP では楽観ロックなし（同一利用者の同時編集はまれと仮定）。将来 `version` カラム導入を検討

## 5. API 基本設計

### 5.1 API 一覧
| メソッド | パス | 概要 | 認証 |
|---|---|---|---|
| `POST` | `/api/auth/login` | OIDC Authorization Request を開始 | 不要 |
| `GET` | `/api/auth/callback` | OIDC コールバック処理 | 不要 |
| `POST` | `/api/auth/logout` | セッション破棄 | 必要 |
| `GET` | `/api/me` | 現在の利用者情報を取得 | 必要 |
| `DELETE` | `/api/me` | アカウント削除 | 必要 |
| `GET` | `/api/diary-entries` | 一覧（年月フィルタ） | 必要 |
| `GET` | `/api/diary-entries/{date}` | 指定日のエントリを取得 | 必要 |
| `POST` | `/api/diary-entries` | 当日のエントリ作成 | 必要 |
| `PUT` | `/api/diary-entries/{date}` | 指定日のエントリ更新 | 必要 |
| `DELETE` | `/api/diary-entries/{date}` | 指定日のエントリ削除 | 必要 |

詳細仕様（パラメータ・レスポンス・エラーコード）は [詳細設計書 §3](../detail-design/詳細設計書.md#3-api-詳細設計) と [`detail-design/api/openapi.yaml`](../detail-design/api/openapi.yaml) を参照。

### 5.2 API 設計方針
- スタイル: **REST**（リソース指向、HTTP メソッドで操作を表現）
- 命名: ケバブケース、複数形（`diary-entries`）
- バージョニング: パスプレフィックスで `v1`（MVP は `/api` 直下、v2 以降で `/api/v1` を導入）
- レスポンス形式: JSON、エラー時は `{ "code": "...", "message": "..." }`

### 5.3 認証・認可方式
- **認証**: OIDC Authorization Code Flow + PKCE で IdP 認証 → サーバ側セッション発行
- **セッション保持**: httpOnly / Secure / SameSite=Lax Cookie（`sid=<opaque token>`）
- **認可**: 全 API で「セッションの所有 User == リソースの所有 User」を検証
- **CSRF**: SameSite=Lax + 状態変更 API は Origin チェック / トークン照合

## 8. セキュリティ基本設計

### 8.1 認証・認可
- 認証: OIDC（Google）、SSO 専用
- 認可: 「セッション利用者 == リソース利用者」原則
- セッション: サーバ側で revoke 可能（Cookie に opaque token、ハッシュ化して DB 保管）

### 8.2 データ保護方針
| 種別 | 機密度 | 保護策 |
|---|---|---|
| 表示名 / メールアドレス | 中 | TLS + DB 暗号化 |
| 日記本文 | **高** | TLS + DB 暗号化、ログ出力禁止 |
| セッショントークン | 高 | DB にハッシュのみ保存（平文不可） |
| OIDC クライアントシークレット | 高 | KMS / Secrets Manager |

### 8.3 脅威モデリング（概要）
STRIDE 観点で主要脅威を整理。詳細対応は [詳細設計書 §7](../detail-design/詳細設計書.md#7-セキュリティ詳細)。
| 脅威 | 例 | 主対策 |
|---|---|---|
| Spoofing | セッション乗っ取り | httpOnly / Secure Cookie、短い有効期限 |
| Tampering | リクエスト改ざん | TLS、サーバ側検証 |
| Repudiation | 改変否認 | 監査ログ |
| Information Disclosure | 他人の日記閲覧 | 認可チェック、暗号化 |
| Denial of Service | 大量リクエスト | レートリミット、CDN |
| Elevation of Privilege | 権限昇格 | 管理機能なし、最小権限の原則 |

> **※ MVP の現在の決定**: 上表で挙げた CDN は **MVP では不採用**（[ADR 0005](../decisions/0005-waf-cdn-deferred.md)）。DoS 対策はアプリ層のレートリミット + GCP インフラ層の組み込み保護で代替する。将来見直しトリガーは ADR 0005 を参照。

## 9. 非機能 / 運用基本設計

### 9.1 ログ設計方針
| 種別 | 内容 | 保管 |
|---|---|---|
| アプリケーション | エラー・主要処理 | 90日 |
| アクセス | HTTP リクエスト | 90日 |

### 9.2 監視・アラート方針
| メトリクス | 閾値 | 通知先 |
|---|---|---|
| API エラー率 | 5分平均 1% 超 | Slack #alerts |
| API レイテンシ p95 | 1秒 超 | Slack #alerts |
| DB 接続失敗 | 1分以内に1回でも | PagerDuty |
| SLO バーンレート | 速い消費 | Slack #alerts |

### 9.3 バックアップ・リストア方針
- DB: 1時間毎スナップショット、世代7日、別リージョンへ複製
- リストアリハーサル: 四半期に1回
