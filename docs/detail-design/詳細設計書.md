## 3. API 詳細設計

### 3.1 共通仕様
- ベース URL: `/api`
- フォーマット: JSON
- 認証: Cookie `sid`（httpOnly / Secure / SameSite=Lax）
- エラー形式: `{ "code": "E_XXX", "message": "..." }`
- 日時: ISO 8601 (UTC)、日付は `YYYY-MM-DD`

詳細は [`api/openapi.yaml`](api/openapi.yaml) に OpenAPI 3.0 で記述。

### 3.2 エラーコード一覧
| コード | HTTP | 意味 |
|---|---|---|
| `E_AUTH_REQUIRED` | 401 | 未認証 |
| `E_FORBIDDEN` | 403 | 認可エラー |
| `E_NOT_FOUND` | 404 | リソースなし |
| `E_DIARY_DUPLICATE` | 409 | 既に当日エントリあり |
| `E_VALIDATION` | 422 | バリデーションエラー |
| `E_RATE_LIMITED` | 429 | レートリミット |
| `E_INTERNAL` | 500 | サーバ内部エラー |
| `E_OIDC_INVALID` | 400 | OIDC 検証失敗（state/nonce/署名） |

### 3.3 主要エンドポイント詳細

#### `POST /api/auth/login`
OIDC Authorization Request を開始し、ブラウザをリダイレクトする。
- リクエスト: なし
- レスポンス: `302 Found`、`Location: https://accounts.google.com/o/oauth2/v2/auth?...`
- サーバ内処理: `state` / `nonce` / PKCE code_verifier を生成して短期セッションに保存

#### `GET /api/auth/callback?code=...&state=...`
OIDC コールバック。
- 検証: `state` 照合、認可コードを Token Endpoint で交換、ID Token 検証（`iss` / `aud` / `exp` / `nonce` / 署名）
- 成功: User を特定/作成 → セッション発行 → Set-Cookie `sid` → `302` で `/`
- 失敗: `400 E_OIDC_INVALID`

#### `POST /api/auth/logout`
- 動作: 現セッションを `revoked_at = now()` に更新、Cookie `sid` を `Max-Age=0` で削除
- レスポンス: `204 No Content`

#### `GET /api/me`
- レスポンス: `{ "id": 1, "displayName": "...", "email": "...", "createdAt": "..." }`

#### `DELETE /api/me`
- 動作: 自分自身の User と関連レコード（SsoIdentity / Session / DiaryEntry）を CASCADE 削除
- レスポンス: `204 No Content`

#### `GET /api/diary-entries?year=2026&month=05`
- レスポンス: `[{ "date": "2026-05-01", "title": "..." }, ...]`（本文は含めない、一覧用）
- ページング: MVP では年月単位、最大1ヶ月分

#### `GET /api/diary-entries/{date}`
- パス: `{date}` は `YYYY-MM-DD`
- レスポンス: `{ "date": "2026-05-01", "title": "...", "body": "...", "createdAt": "...", "updatedAt": "..." }`
- 404: 該当日のエントリなし

#### `POST /api/diary-entries`
- リクエスト: `{ "title": "...", "body": "..." }`（`date` はサーバ側で当日に固定）
- レスポンス: `201 Created`、`Location: /api/diary-entries/{date}`
- エラー: `409 E_DIARY_DUPLICATE`（当日分が既にある）

#### `PUT /api/diary-entries/{date}`
- リクエスト: `{ "title": "...", "body": "..." }`
- レスポンス: `200 OK`、更新後のエントリを返す
- エラー: `404 E_NOT_FOUND`、`403 E_FORBIDDEN`（他人のエントリ）

#### `DELETE /api/diary-entries/{date}`
- レスポンス: `204 No Content`

### 3.4 レートリミット
| エンドポイント | 制限 |
|---|---|
| `POST /api/auth/login` | 10 req/min/IP |
| `GET /api/auth/callback` | 20 req/min/IP |
| 認証後の全 API | 600 req/min/利用者 |

## 4. データベース詳細設計

[`table/tables.md`](table/tables.md) を参照。

主要ポイント:
- DDL は PostgreSQL 16 想定
- すべての PK は `bigint` の連番 (`generated always as identity`)
- 文字列は基本 `text`（長さ制約はアプリ層で）
- タイムスタンプは `timestamptz`

### 4.1 マイグレーション方針
- ツール: 例として `prisma migrate` / `sqldef` / `flyway` のいずれか（実装時決定）
- 後方互換性: 列追加 → デフォルト埋め → NOT NULL 化、の3段階デプロイ
- ロールバック: スキーマは前方互換、データ補正はマイグレーションスクリプトで

### 4.2 代表クエリ
```sql
-- 当日エントリの存在チェック
SELECT id FROM diary_entries
WHERE user_id = $1 AND entry_date = CURRENT_DATE;

-- 月単位の一覧
SELECT entry_date, title FROM diary_entries
WHERE user_id = $1
  AND entry_date >= $2::date
  AND entry_date <  ($2::date + INTERVAL '1 month')
ORDER BY entry_date DESC;
```

## 7. セキュリティ詳細

### 7.1 STRIDE 対応表
| 脅威 | シナリオ | 対策 |
|---|---|---|
| Spoofing | 他人のセッション Cookie 流用 | httpOnly / Secure / SameSite=Lax、IP変化検知（将来） |
| Tampering | リクエストボディ改ざん | TLS、サーバ側スキーマ検証 |
| Repudiation | 「自分は削除していない」主張 | 監査ログに削除操作を記録 |
| Information Disclosure | 他人の日記閲覧 | 全 API で `userId == session.userId` を検証 |
| Denial of Service | 大量リクエスト | レートリミット §3.4、CDN |
| Elevation of Privilege | 管理者権限取得 | 管理者画面・API を実装しない |

### 7.2 OWASP Top 10 対策（抜粋）
| 項目 | 対策 |
|---|---|
| A01 アクセス制御の不備 | 全 API で所有者チェック、デフォルト deny |
| A02 暗号化失敗 | TLS 1.2+、DB at-rest 暗号化、シークレットは KMS |
| A03 インジェクション | ORM / プリペアドステートメント、入力検証 |
| A05 設定ミス | デフォルトパスワード排除、不要ポート閉鎖、IaC で固定 |
| A07 識別と認証の失敗 | SSO 専用、セッション有効期限、ログアウト時失効 |

### 7.3 SSO（OIDC）実装詳細
- **PKCE**: code_verifier はランダム 43-128 文字、`code_challenge_method=S256`
- **state**: CSRF 防止に必須、ランダム32バイト Base64URL、コールバックで照合
- **nonce**: ID Token 検証で照合、リプレイ防止
- **ID Token 検証順序**:
  1. JWT 形式・署名検証（JWKS から取得した公開鍵）
  2. `iss == https://accounts.google.com`
  3. `aud == 設定済み client_id`
  4. `exp > now()`
  5. `nonce == 保存値`
- **アカウント紐付け**:
  - `(provider='google', provider_subject=sub)` で既存 SsoIdentity を検索
  - あり → 紐付く User のセッション発行
  - なし → User と SsoIdentity を新規作成（同一トランザクション）

### 7.4 秘密情報管理
| 情報 | 保管場所 |
|---|---|
| OIDC `client_secret` | クラウド Secrets Manager / Vault |
| DB 接続情報 | 同上 |
| セッショントークン | DB には**ハッシュのみ**、原文は Cookie のみ |

## 8. インフラ詳細

### 8.1 IaC 構成
- ツール: Terraform を推奨（クラウド非依存の知見が広い）
- リポジトリ構成（別リポジトリ想定）:
  ```
  infra/
  ├── modules/
  │   ├── network/
  │   ├── compute/
  │   ├── database/
  │   └── secrets/
  └── envs/
      ├── dev/
      ├── stg/
      └── prd/
  ```

### 8.2 ネットワーク詳細（クラウド汎用）
- VPC: パブリックサブネット（LB/CDN）+ プライベートサブネット（App/DB）
- SG: LB → App は HTTPS、App → DB は単一ポート、外向きは Google OIDC のみ許可
- WAF: マネージドルールセット適用

### 8.3 スケーリング
- Web/API: コンテナをオートスケール（CPU 70% を上限指標）
- DB: 縦スケール優先、リードレプリカは段階導入

### 8.4 CI/CD 詳細
| ステージ | 内容 | 失敗時 |
|---|---|---|
| Lint | ESLint / Prettier | マージ不可 |
| Unit Test | カバレッジ 70% 以上 | マージ不可 |
| Build | コンテナイメージビルド | 中断 |
| Stg Deploy | 自動 | ロールバック |
| E2E (Stg) | 主要ハッピーパス | 通知 + 手動判断 |
| Prd Deploy | 手動承認後 Blue/Green | 自動切り戻し |

## 9. 運用設計詳細

### 9.1 リリース手順
1. リリース PR をマージ
2. CI が ステージングへ自動デプロイ
3. ステージングで動作確認
4. 「本番デプロイ」承認をクリック
5. Blue/Green で切替、5分監視
6. 異常なければ完了、異常時は自動切り戻し

### 9.2 障害対応ランブック（抜粋）
| 症状 | 切り分け | 復旧 |
|---|---|---|
| 全 API 5xx 増加 | LB ヘルス確認 → App ログ確認 | 直前デプロイなら切り戻し |
| ログインが進まない | Google OIDC ステータス → アプリ側エラーログ | IdP 障害なら告知、自前なら設定/シークレット確認 |
| DB 接続失敗 | DB エンドポイント疎通、メンテ状況 | フェイルオーバー or リストア |

### 9.3 監視ルール詳細
| ルール | 条件 | 通知 |
|---|---|---|
| HighErrorRate | 5分間 API エラー率 1% 超 | Slack |
| HighLatency | p95 1秒超が5分継続 | Slack |
| DbConnFailure | 直近1分以内に接続失敗1件以上 | PagerDuty |
| SloBurn | 1時間で1日相当のエラー予算消費 | Slack |

## 10. テスト設計

### 10.1 テスト戦略
| レベル | 目的 | 対象 | 自動化 |
|---|---|---|---|
| Unit | 関数・モジュール単位の正しさ | バリデーション・ドメインロジック | ◯ |
| Integration | DB / 外部 API を含む結合 | リポジトリ / OIDC 検証 | ◯ |
| E2E | ユーザー導線の通り | 主要ハッピーパス・ログイン | ◯ |
| 性能 | レイテンシ・スループット | 認証後の主要 API | △（定期） |
| セキュリティ | 脆弱性 | 依存・SAST / DAST | ◯（CI） |

### 10.2 重点観点
- **認証フロー**: state/nonce/PKCE 検証ロジック、ID Token 改ざん耐性
- **認可**: 他人のエントリへの操作で 403 が返るか
- **1日1エントリ制約**: 同一日 POST 連打で 409 が返るか、並列でも DB UNIQUE で1件のみ
- **境界値**: タイトル 0/1/100/101 文字、本文 0/1/10000/10001 文字
