# 技術スタック決定インタビュー

各質問に答えていくと、技術スタックの主要な選択が決まります。回答は [`decision-record.md`](decision-record.md) の表に記入してください。Claude に進めてもらう場合は「tech-stack のインタビューを進めて」と依頼。

## 質問の体裁

各質問は **目的 / 選択肢 / 推奨デフォルト / 参考** の4要素で構成。選択肢は `A` `B` `C` `D` の形で番号付け（`decision-record.md` ではこの記号で参照する）。

---

## A. プロジェクト前提

### Q-PRJ-01: プロジェクト規模と期間は？
**目的**: スタックの保守性・学習コスト許容度を決める。
**選択肢**:
- A. **PoC / 短期 (1〜3ヶ月)** — 速度最優先、後で書き直し前提
- B. **本番運用・中期 (半年〜2年)** — 保守性重視
- C. **長期運用 (3年以上)** — 安定性・後方互換性最優先
- D. **継続改善型** — 期間より「変更容易性」を優先

**推奨デフォルト**: B
**参考**: [catalog.md](catalog.md)

### Q-PRJ-02: チームの既存スキルは？
**目的**: 学習コストとデリバリ速度のトレードオフ。
**選択肢**:
- A. **既存スキル優先** — チームが慣れた技術をそのまま採用
- B. **適度な新技術** — 既存7〜8割 + 学習要素2〜3割
- C. **大胆に刷新** — 採用したい技術を主軸に学びながら進める

**推奨デフォルト**: A

### Q-PRJ-03: 予算・運用コストの制約は？
**目的**: マネージドサービスの採用範囲を決める。
**選択肢**:
- A. **コスト最小化** — 自前運用多め、無料枠活用
- B. **バランス** — 価格と運用負荷をバランス
- C. **運用負荷最小化** — マネージドサービス積極採用、コストは許容

**推奨デフォルト**: B

### Q-PRJ-04: ベンダーロックインの許容度は？
**目的**: クラウド固有サービス採用の可否。
**選択肢**:
- A. **避けたい** — OSS / 移植性重視
- B. **特定領域は許容** — DB やストレージは固有サービスを許可
- C. **積極的に活用** — 開発速度優先で固有サービスを多用

**推奨デフォルト**: B

## B. フロントエンド

### Q-FE-01: レンダリング戦略は？
**目的**: SEO・初期表示・運用コストのバランス。
**選択肢**:
- A. **SSR** — Server-Side Rendering。SEO / 初期表示重視（Next.js / Nuxt / SvelteKit）
- B. **SPA** — Single Page Application。内部ツール / 認証必須サービス（React / Vue / Svelte + Vite）
- C. **SSG** — Static Site Generation。コンテンツが少なく更新頻度低
- D. **ハイブリッド** — ISR / PPR で動的部分のみ更新

**推奨デフォルト**: A
**参考**: [catalog.md §フロントエンド](catalog.md#フロントエンド)

### Q-FE-02: UI フレームワークは？
**目的**: UI 構築の基盤を決める。
**選択肢**:
- A. **React** — エコシステム最大
- B. **Vue** — 学習曲線がゆるい
- C. **Svelte / SvelteKit** — 軽量・パフォーマンス
- D. **その他（Solid / Qwik / Vanilla）** — 特殊要件向け

**推奨デフォルト**: A

### Q-FE-03: CSS 手法は？
**選択肢**:
- A. **Tailwind CSS** — ユーティリティクラス
- B. **CSS Modules** — スコープ付き
- C. **CSS-in-JS** — Emotion / styled-components
- D. **Vanilla CSS** — シンプル・依存最小

**推奨デフォルト**: A

### Q-FE-04: 状態管理は？
**選択肢**:
- A. **フレームワーク標準** — React Context / Vue Pinia
- B. **専用ライブラリ** — Zustand / Jotai / Redux Toolkit
- C. **サーバ状態に寄せる** — TanStack Query / SWR
- D. **不要** — 規模が小さい

**推奨デフォルト**: C（サーバ状態） + A（局所 UI 状態）

## C. バックエンド

### Q-BE-01: 言語は？
**選択肢**:
- A. **TypeScript (Node.js)** — フロントと言語統一
- B. **Python** — 機械学習・データ処理が絡む
- C. **Go** — 高パフォーマンス・シンプル
- D. **その他（Rust / Java / Kotlin / C#）** — 既存資産・要件次第

**推奨デフォルト**: A（フロントが TS の場合）

### Q-BE-02: API スタイルは？
**選択肢**:
- A. **REST** — 標準的、学習コスト低
- B. **GraphQL** — 複数クライアント / 柔軟なクエリ
- C. **gRPC** — マイクロサービス間 / 高性能 RPC
- D. **tRPC** — TS フルスタックの型共有

**推奨デフォルト**: A

### Q-BE-03: フレームワークは？（TS 採用時）
**選択肢**:
- A. **Fastify** — 高速・最小限
- B. **Hono** — Edge / Workers にも対応
- C. **NestJS** — 大規模向け、DI / モジュール
- D. **Express** — 知見が豊富だが古典的

**推奨デフォルト**: A

### Q-BE-04: 非同期 / バックグラウンドジョブの必要性は？
**選択肢**:
- A. **不要** — 同期処理のみで完結
- B. **軽量ジョブキュー** — BullMQ / Sidekiq 等
- C. **メッセージブローカ** — Kafka / RabbitMQ / NATS
- D. **クラウド管理サービス** — SQS / Pub/Sub / Service Bus

**推奨デフォルト**: A（MVP）→ 段階的に B

## D. データ層

### Q-DATA-01: データストアの種類は？
**選択肢**:
- A. **RDB のみ** — 整合性重視
- B. **NoSQL のみ** — スキーマ柔軟性 / スケール重視
- C. **RDB + NoSQL 併用** — 用途で分ける
- D. **RDB + 検索** — 全文検索を別系統で

**推奨デフォルト**: A

### Q-DATA-02: DBMS は？
**選択肢**:
- A. **PostgreSQL** — 機能豊富、JSON も扱える
- B. **MySQL / MariaDB** — シンプル、知見豊富
- C. **SQLite** — 単一プロセス / 軽量
- D. **マネージド NewSQL** — Spanner / CockroachDB

**推奨デフォルト**: A

### Q-DATA-03: キャッシュは？
**選択肢**:
- A. **不要** — DB で十分
- B. **インメモリ** — アプリ内キャッシュ
- C. **Redis / Memcached** — 共有キャッシュ
- D. **CDN キャッシュのみ** — 配信レイヤで吸収

**推奨デフォルト**: A（MVP）

### Q-DATA-04: 全文検索は？
**選択肢**:
- A. **不要** — LIKE / FTS で足りる
- B. **DB の組み込み** — PostgreSQL `tsvector` 等
- C. **専用エンジン** — OpenSearch / Elasticsearch / Meilisearch
- D. **マネージド検索** — Algolia / Typesense Cloud

**推奨デフォルト**: A

## E. 認証・認可

### Q-AUTH-01: 認証方式は？
**選択肢**:
- A. **SSO (OIDC / OAuth)** — 外部 IdP に委譲
- B. **メール + パスワード** — 自前で管理
- C. **両方併存** — SSO 優先 + メールも残す
- D. **マジックリンク / OTP** — パスワードレス

**推奨デフォルト**: A

### Q-AUTH-02: 認可モデルは？
**選択肢**:
- A. **シンプル所有者** — 「自分のリソースだけ」
- B. **RBAC** — ロールベース
- C. **ABAC** — 属性ベース、柔軟
- D. **ReBAC** — 関係ベース（Google Zanzibar 型）

**推奨デフォルト**: A（MVP）

## F. 監視・ログ

### Q-OBS-01: 監視の3点セットは？
**選択肢**:
- A. **メトリクス + ログ** — トレースは省略
- B. **3点セット (Metrics + Logs + Traces)** — OpenTelemetry
- C. **クラウド標準** — CloudWatch / Cloud Monitoring 等
- D. **SaaS** — Datadog / New Relic / Grafana Cloud

**推奨デフォルト**: A（MVP）→ B（成熟期）

### Q-OBS-02: エラートラッキングは？
**選択肢**:
- A. **不要** — ログで対応
- B. **Sentry** — 定番
- C. **Rollbar / Bugsnag** — 代替
- D. **クラウド標準** — Error Reporting / Application Insights

**推奨デフォルト**: B

### Q-CI-01: CI/CD ツールは？
**選択肢**:
- A. **GitHub Actions** — GitHub 完結
- B. **GitLab CI** — GitLab 完結
- C. **CircleCI / Buildkite** — 専用 SaaS
- D. **クラウド標準** — CodePipeline / Cloud Build
